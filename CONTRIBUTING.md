# Contributing to Ferrion

Thanks for your interest in Ferrion. This document covers how contributions are licensed, the
clean-room policy every contribution must follow, and how to build and test the project.

What Ferrion is and is not is defined in [docs/SCOPE.md](docs/SCOPE.md), and the order of work is
in [docs/ROADMAP.md](docs/ROADMAP.md). A change that would alter the scope starts as a change to
SCOPE.md, discussed in an issue before any code is written.

## Licensing

Ferrion is dual-licensed under the [MIT License](LICENSE-MIT) and the
[Apache License, Version 2.0](LICENSE-APACHE), at the user's option.

Unless you explicitly state otherwise, any contribution you intentionally submit for inclusion in
Ferrion, as defined in the Apache-2.0 license, is dual-licensed as above, without any additional
terms or conditions.

Source files do not carry license headers. The license files at the repository root cover
everything in it, except third-party code that keeps its own notice (see
[Code you may copy](#code-you-may-copy)).

## Clean-room policy

Ferrion replaces tools such as Google Java Format, Checkstyle, PMD, Error Prone, and SpotBugs, and it
is checked against javac. Most of those tools are licensed in ways that are not compatible with
Ferrion's licensing. Ferrion must be an independent implementation, so every contribution follows
this policy.

Automated checks (ScanCode in CI) catch copied license notices and copyright statements, but they
cannot detect copied code without them, or a port from Java to Rust. This policy, and the checklist item in the pull-request
template, are the main safeguards.

### What you may use

- **Documentation:** user guides, rule descriptions, and published style guides of upstream tools.
- **Specifications:** the Java Language Specification, the Java Virtual Machine Specification, JEPs,
  and similar documents. Cite them by section number in comments rather than quoting them at length.
- **Observable behavior:** running an upstream tool and studying what it produces. "What does javac
  report for this input?" is answered by running javac, and the answer becomes a test.
- **Names and concepts:** rule names, option names, and general ideas. Rule documentation is written
  in your own words and may link to the upstream documentation it relates to.
- **Test inputs fetched at test time:** externally licensed test suites (for example, OpenJDK's) may
  be downloaded by test tooling. They are never committed (see
  [Test inputs](#test-inputs)).

### What you may not do

- **Copy** code from a project whose license is not compatible (see
  [Code you may copy](#code-you-may-copy)). That includes code, comments, test files, and
  documentation text.
- **Port** such code: translating it from Java (or any other language) to Rust, or reproducing its
  structure, control flow, or data layout, even if every line is rewritten.
- **Work from the source:** have upstream source code open, or consult it, while writing the
  equivalent part of Ferrion. If a question can only be answered by reading upstream source, answer
  it by running the tool on test inputs instead.
- **Ask an AI assistant to do any of the above.** Code generated by an AI tool is your contribution
  and falls under this policy. Do not prompt a tool to port, translate, or reproduce upstream code,
  and review generated code with that risk in mind.

If you have studied an upstream tool's implementation of something in depth, say so in your pull
request before contributing an implementation of the same thing. That's not automatically a problem,
but it needs to be visible.

### Code you may copy

Code from another project may be copied only if its license allows it to be distributed under both
MIT and Apache-2.0. In practice, that means permissive licenses such as MIT, BSD-2-Clause,
BSD-3-Clause, ISC, and Zlib. Code licensed only under Apache-2.0 does not qualify on its own, because
it could not be offered under MIT. Copyleft licenses (GPL, LGPL, EPL, MPL) never qualify.

When you copy qualifying code:

- keep its copyright and license notice next to the copied code;
- say in the pull request where it came from and under what license;
- prefer depending on the project as a crate over copying, when that's practical.

### Test inputs

- Write your own test inputs where you can. Small, focused inputs make better tests anyway.
- Files from projects with incompatible licenses (for example, OpenJDK's GPL test suites, or test
  files from Checkstyle, PMD, or SpotBugs) are fetched by the test tooling at test time and are
  never committed.
- Corpus projects are fetched by `tools/corpus`, pinned to a commit. Nothing it fetches is
  committed.
- Expected output generated by running an upstream tool on Ferrion's own test inputs may be
  committed.

### Dependencies

Third-party crates are welcome if they pass `cargo deny check`, which enforces the allowed license
list in CI. The same rule applies to dependencies of the Maven plugin and the IntelliJ extension.
The lexer and parser are hand-written; parser generators are not used.

### Reporting a concern

If you believe something in Ferrion was copied or ported in violation of this policy, open an issue.
Concerns are taken seriously, and code with unclear provenance is removed or rewritten.

## Development

### Prerequisites

- **Rust:** install [rustup](https://rustup.rs). The toolchain version is pinned in
  `rust-toolchain.toml`, and rustup installs it automatically.
- **A JDK:** needed only for the javac oracle and corpus tools. Use the newest GA release to cover
  the latest language features.
- **Maven:** needed only for the javac oracle and the Maven plugin.
- **Python 3.13 and libmagic:** needed only to run ScanCode locally. On macOS, install libmagic with
  `brew install libmagic`.

### Checks

CI runs the following, and each must pass before a change is merged:

```bash
cargo fmt --all --check
```

```bash
cargo clippy --workspace --all-targets -- -D warnings
```

```bash
cargo test --workspace
```

```bash
cargo deny check
```

```bash
cargo deny --manifest-path fuzz/Cargo.toml check
```

```bash
python3 tools/scancode/scan.py
```

The ScanCode check installs its pinned dependencies from `tools/scancode/requirements.txt` into
`target/scancode/venv`, then fails on any license other than MIT or Apache-2.0, or any copyright
holder other than Ferrion's.

### Corpus

The corpus projects are listed in `tools/corpus/projects.toml`, each pinned to a commit. They are
fetched into `target/corpus`, or into `FERRION_CORPUS_DIR` if it is set:

```bash
cargo corpus fetch
```

Each project's lock file in `tools/corpus/lock/` records its source sets, Java releases, and
dependency jars, so fetching never runs a project's build. After adding a project or changing its
commit, regenerate its lock file with `JAVA_HOME` set to the JDK named in `projects.toml`. This runs
the project's own build:

```bash
cargo corpus lock <project>
```

Name resolution reads a fetched project through a project model written from its lock, to
`target/corpus/models/<project>.json`, with the JDK given (default: `JAVA_HOME`, which should be
the newest GA JDK) for every source set. See
[docs/design/project-inputs.md](docs/design/project-inputs.md#corpus-models):

```bash
cargo corpus project-model --jdk ~/.local/share/mise/installs/java/temurin-27 <project>
```

OpenJDK's javac tests are parser inputs too. Like the other incompatibly licensed test suites,
they're fetched at test time, at the tag pinned in `tools/corpus/jdk-tests.toml`, into
`target/corpus/jdk-tests` (or under `FERRION_CORPUS_DIR`), and never committed. Only the test
directories are checked out, from a partial clone, so no implementation source is downloaded:

```bash
cargo corpus jdk-tests
```

`cargo corpus jdk-tests list` prints each input with the releases its jtreg header compiles it
at. `tools/corpus/jdk-tests-deep-nesting.txt` lists javac's deep-nesting stress tests among them,
by path; see [docs/design/parser-oracle-normalization.md](docs/design/parser-oracle-normalization.md)
for how they were chosen. Don't study the tests beyond what selecting and running them needs.
Finding the construct at a reported mismatch is part of running them; record it as a known
difference with an input of your own, written from javac's output rather than from the test, and
list the test by path in `tools/oracle-check/differences/known-files.txt`.

### javac oracle

`tools/javac-oracle` dumps javac's tokens, comments, scanner diagnostics, parse diagnostics (with
their codes and arguments), and tree positions as JSON lines. Build it with the newest GA JDK:

```bash
mvn --batch-mode --file tools/javac-oracle/pom.xml package
```

```bash
java -jar tools/javac-oracle/target/javac-oracle.jar --release 17 Example.java
```

`--sections tokens,comments` limits the output to the named sections (`tokens`, `comments`,
`scanDiagnostics`, `diagnostics`, `tree`), and `@files.txt` reads paths from a file, one per line.

`tools/oracle-check` compares Ferrion with the oracle across the corpus. With `JAVA_HOME` set to
the newest GA JDK, the oracle built, and the corpus checked out (`cargo corpus checkout`, which
skips the jars), compare the lexer's tokens with javac's, and check that they reproduce each file:

```bash
cargo oracle tokens
```

By default, each file is compared at its source set's release, as in pull-request CI. Name
projects to compare only those, `--release <N>` to compare every file at release N,
`--primary-releases` for each primary release (the LTS releases and the latest; see
[docs/SCOPE.md](docs/SCOPE.md)), which a scheduled workflow runs weekly, or `--all-releases` for
every supported release. `--file <path>` compares a file of your own, `--json <file>` writes the
full report, and `--help` lists the other options. Any mismatch fails the run; the normalization
and the allowed differences are in [docs/design/lexer-oracle-normalization.md](docs/design/lexer-oracle-normalization.md).

javac's output is cached in `target/oracle`, or in `FERRION_ORACLE_CACHE` if it is set, keyed by
the oracle jar, the JDK, the release, and each file's content, so a rerun only runs javac for what
changed. Delete the directory to start over.

Differences on input the corpus doesn't have, such as malformed literals, are checked against
snapshots in `tools/oracle-check/differences/`:

```bash
cargo oracle differences
```

It fails if javac's output or the lexer's no longer matches a snapshot. When a change is intended,
`cargo oracle differences --bless` rewrites the snapshots; update the "Known differences on
malformed input" section of the normalization document to match. `cargo test` checks the lexer's
side of the snapshots without a JDK.

The parser's checks run the same way: `syntax` compares the first syntax error with javac's, and
`tree` compares every node:

```bash
cargo oracle syntax
```

```bash
cargo oracle tree
```

Besides corpus projects, both take `jdk-tests`, javac's tests fetched by `cargo corpus jdk-tests`,
each compared at the releases its test compiles it at, and `jdk-deep-nesting`, javac's
deep-nesting stress tests. Snapshots of javac's parser output on small inputs, which
[docs/design/parser-oracle-normalization.md](docs/design/parser-oracle-normalization.md) cites,
are in `tools/oracle-check/parser-cases/`:

```bash
cargo oracle parser-cases
```

It fails if javac's output no longer matches a snapshot; `--bless` rewrites them, and the document
is updated to match.

### Parser checks

`tools/parser-check` checks the parser on the corpus without javac. With the projects checked out,
parse every file at its source set's release, check that the tree reproduces it byte for byte and
keeps the parser's invariants, and report throughput:

```bash
cargo parser-check round-trip
```

Like `cargo oracle`, it takes project names, `jdk-tests`, and `jdk-deep-nesting`; javac's tests are
parsed at the releases their tests compile them at. Any failure fails the run; syntax errors only
are counted, since the oracle comparison decides which are right. `--verbose` prints each file
before parsing it, to find one that aborts the process.

The corpus mutation test measures error recovery, as
[docs/design/parser-error-recovery.md](docs/design/parser-error-recovery.md) describes. It breaks
files at seeded random tokens, checks each broken file as `round-trip` does, and measures the share
of declarations, statements, and imports recovery preserves, per kind of mutation:

```bash
cargo parser-check mutate --seed 1 --sample 2000
```

The run fails if a share is below its threshold in `tools/parser-check/thresholds.toml`. When
recovery improves, raise the thresholds to a little below the new measurements of the sample above
and of the weekly one (`--seed 2 --sample 20000`), as the file explains. `--verbose` lists the first declarations lost (`--limit` sets how many), with the mutation
that lost them.

### Format checks

`tools/format-check` checks the formatter on the corpus. With the projects checked out, format
every file at its source set's release, check the four safety properties of
[docs/SCOPE.md](docs/SCOPE.md) on each output, and report throughput and peak memory:

```bash
cargo format-check verify
```

Like `cargo parser-check`, it takes project names, `jdk-tests`, and `jdk-deep-nesting`. Any
failure fails the run; files with syntax errors are skipped and counted.

The formatter's style follows Google Java Format 2.0.0, pinned in `tools/format-check/gjf.toml`
and downloaded on first use into the corpus's jar cache. Never read GJF's source; learn what it
does by running it, and write down what you find (see
[docs/design/formatter.md](docs/design/formatter.md)). With `JAVA_HOME` set to Temurin 27, compare
Ferrion's output with GJF's for each corpus file, and print the files compared and identical, the
lines that differ, the largest differences, and a sample of hunks:

```bash
cargo format-check gjf
```

`--check` fails if a project's differing lines are above the number committed in
`tools/format-check/gjf-diff.toml`. A change that lowers them records the new numbers with
`--update`. Each departure from GJF has a case in `tools/format-check/differences/`: an input,
GJF's output (`.gjf`), and Ferrion's (`.ferrion`). Check that both tools still produce them:

```bash
cargo format-check differences
```

When the GJF pin moves, `--bless` rewrites GJF's outputs. Ferrion's are written by hand, from the
departure's entry in `docs/style.md`.

The formatter's snapshots record GJF's style: check that each snapshot's expected output is GJF's
output for its input, for every area or the ones named:

```bash
cargo format-check snapshots statements
```

A snapshot that isn't GJF's on purpose, for a departure or because its area's rules aren't written
yet, is listed in `NOT_GJF` in `tools/format-check/src/snapshots.rs` with the reason.

### javap oracle

`tools/javap-oracle` checks the class file reader (`crates/ferrion_classfile`) against the JDK's
own tools, through public APIs only. It runs `javap -v -p` in process and normalizes its output,
digests what the jrt file system, `ZipFile`, and `JarFile` return for each file of a container, and
lists what javac sees with `--release` through the javac API. It runs on JDK 11 and later; build it
with the newest GA JDK:

```bash
mvn --batch-mode --file tools/javap-oracle/pom.xml package
```

`cargo oracle classfile` compares Ferrion's reading with it. With `JAVA_HOME` set to the newest GA
JDK, which runs javap for every input, check a JDK's every release, its image against jrt, its
`ct.sym` (or JDK 8's jars) against `ZipFile`, and, for JDK 11 and later, what javac sees with each
`--release`:

```bash
cargo oracle classfile --jdk ~/.local/share/mise/installs/java/corretto-21.0.11.10.1
```

`--jdk` is repeatable, and `--release <N>` limits the releases checked. Without `--jdk`, or with
project names, the corpus projects' dependency jars are checked (fetch them first with `cargo
corpus fetch`): as zips, as jars at each source set's release against `JarFile`, and each class
with javap. Each distinct class is compared with javap once per run, and javap's output is cached
in `target/oracle/javap`. The weekly oracle workflow runs it on every JDK in the matrix of
[docs/design/classfile.md](docs/design/classfile.md#jdks-and-vendors) and on every project's jars;
pull requests check the latest JDK's own release and one project's jars. The design document
explains every difference the check allows.

### Benchmarks

`tools/bench` measures the lexer, the parser, the formatter, and class file reading, as
[docs/design/benchmarks.md](docs/design/benchmarks.md) describes. With jedis checked out and its
jars fetched, and `JAVA_HOME` set to a JDK, run every benchmark, or those whose names contain a
filter, and save the results:

```bash
cargo benchmark run --out before.json
```

```bash
cargo benchmark run parser --out after.json
```

Each reports wall time, user and system time, peak RSS, and heap use. On Linux with valgrind,
`--callgrind` also counts instructions. Compare two runs; a metric that grows past its threshold in
`tools/bench/thresholds.toml` fails the comparison:

```bash
cargo benchmark compare before.json after.json
```

Pull requests run this on their base and head in CI, and show the comparison in the job summary. A
new component adds its benchmarks to `tools/bench/src/benchmarks/`.

### Tests

- Every bug fix comes with a regression test.
- Fuzz failures are reduced and kept as regression tests.
- The parser's snapshot tests compare each input in `crates/ferrion_parser/tests/snapshots/` with
  its printed tree. Broken inputs that test recovery go in a `recovery` directory there, and must
  report an error. After an intended change, rewrite the trees and review the diff:

  ```bash
  FERRION_BLESS=1 cargo test --package ferrion_parser --test snapshots
  ```

- The formatter's snapshot tests format each input in
  `crates/ferrion_formatter/tests/snapshots/<area>/` and compare it with the `.formatted.java`
  file next to it, and check the safety properties on it. After an intended change, rewrite the
  outputs and review the diff:

  ```bash
  FERRION_BLESS=1 cargo test --package ferrion_formatter --test snapshots
  ```

- The deep-nesting stress tests in `crates/ferrion_parser/tests/nesting_stress.rs` generate their
  inputs from the patterns in `crates/ferrion_parser/src/stress.rs`. A pattern whose grammar isn't
  written yet is listed in `PENDING` there, and its test fails once it parses without errors, so
  that it's moved out of the list. The tree's consumers run the same patterns: the formatter's
  are in `crates/ferrion_formatter/tests/deep_nesting.rs`. A new pattern gets a test in each.
- Generated rule documentation is checked in CI, so regenerate it when rule metadata changes.

### Generated syntax code

The syntax tree's `SyntaxKind` and typed views (`ferrion_syntax::ast`) are generated from
`crates/ferrion_syntax/java.grammar`, which lists every node kind and its children. After changing
the grammar, regenerate them; CI checks that they're up to date:

```bash
cargo codegen
```

### Fuzzing

The fuzz targets are in `fuzz/`, a [cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz) project
with its own workspace. It builds with the nightly toolchain pinned in `fuzz/rust-toolchain.toml`,
which rustup uses for commands run from `fuzz/`; everything else stays on the stable toolchain. Run
the commands below from `fuzz/`, after installing the toolchain and cargo-fuzz once:

```bash
rustup toolchain install && cargo install cargo-fuzz --version 0.13.2 --locked
```

- `lex` reads arbitrary bytes as a source file and lexes its text.
- `lex_fragments` lexes text built from fragments of Java, such as keywords, comment and text block
  delimiters, and Unicode escapes, to reach states that random bytes rarely do.
- `javadoc` reads arbitrary bytes as the content of a `/** */` comment and parses it with the doc
  comment parser.
- `markdown` reads arbitrary bytes as lines of `///` comments (each line gets the `///`) and parses
  the Markdown doc comments they form.
- `parse` reads arbitrary bytes as a source file and parses its text at each primary release.
- `format` reads arbitrary bytes as a source file, and at each primary release where it parses
  without errors, formats it and checks the four safety properties with `verify`. Its seeds are
  the parser's, in `seeds/parse`.
- `classfile` reads arbitrary bytes as a class file and calls every accessor, decoding every
  attribute, annotation, signature, and descriptor.
- `signature` parses arbitrary text as class, method, and field signatures and as descriptors.
- `zip` reads arbitrary bytes as a zip file and reads every entry; `jar` reads them as a manifest,
  and as a multi-release jar at several releases.
- `jimage` reads arbitrary bytes as a module image and reads every resource; `jimage_structured`
  builds a valid image from the input, in either byte order and with each compression, then
  changes a few bytes, to reach the code random bytes rarely do.
- `ctsym` reads arbitrary bytes as a zip and then as `ct.sym`, resolving every release.
- `semantic_edits` applies edits chosen by the input to a small project, and after each compares
  the semantic engine's summaries and package tables with a fresh engine's. The input's bytes up
  to a first zero byte, if any, are one more file of the project.

The lexer targets fail when `ferrion_lexer::invariants` finds that the lexer broke a promise its API
documents, the doc comment targets when `ferrion_doc_comments::invariants` finds the same of the
doc comment parsers, the `parse` target when `ferrion_parser::invariants` finds the same of the
parser or its tree, the `format` target when `ferrion_formatter::invariants` finds a safety
property broken, the class file targets when `ferrion_classfile::invariants` finds the same of
the class file, container, and platform readers, and `semantic_edits` when
`ferrion_semantic::invariants` finds an answer that differs from a fresh engine's. All of them
fail when the code under test panics, and the parser's debug assertions catch a loop that makes
no progress and an empty node.
Run a target, reading the committed seeds in `seeds/` and keeping what it finds in `corpus/`
(ignored by git):

```bash
mkdir -p corpus/lex && cargo fuzz run --sanitizer none --debug-assertions lex corpus/lex seeds/lex -- -dict=java.dict -timeout=10
```

The lexer, parser, and formatter targets use the dictionary `java.dict`, the doc comment targets
`doc_comments.dict`, and the class file targets `classfile.dict`:

```bash
mkdir -p corpus/javadoc && cargo fuzz run --sanitizer none --debug-assertions javadoc corpus/javadoc seeds/javadoc -- -dict=doc_comments.dict -timeout=10
```

The code under test has no unsafe code, so AddressSanitizer is turned off, which makes fuzzing
about twice as fast; debug assertions catch arithmetic overflow. Pass the same two flags to every
`cargo fuzz` command, or it rebuilds the targets. Add `-max_total_time=<seconds>` after `--` to stop
after a while. CI runs every target for 60 seconds (`.github/workflows/fuzz.yml`, called from
`ci.yml`), and a weekly scheduled run of the same workflow runs each for 30 minutes and keeps its
corpus in the Actions cache. The targets are split over four jobs, each taking every fourth target
in `cargo fuzz list` order and running its targets side by side; a new target needs no workflow
change, unless it reads another target's seeds, as `format` does. Crashing inputs are uploaded as a `fuzz-artifacts-<shard>` artifact.

To turn a failure into a regression test:

1. Minimize the input. `tmin` prints the path of the minimized input:

   ```bash
   cargo fuzz tmin --sanitizer none --debug-assertions lex artifacts/lex/crash-<hash>
   ```

2. Copy it, under a name that says what it covers, to `crates/ferrion_lexer/tests/fuzz-regressions/`
   for a lexer target, `crates/ferrion_parser/tests/fuzz-regressions/` for `parse`,
   `crates/ferrion_formatter/tests/fuzz-regressions/` for `format`,
   `crates/ferrion_doc_comments/tests/fuzz-regressions/javadoc/` or `.../markdown/` for a doc
   comment target, or `crates/ferrion_classfile/tests/fuzz-regressions/<target>/` for a class file
   target. A `lex_fragments` input is a list of fragment numbers,
   not source text, so write its text there instead:

   ```bash
   FERRION_FUZZ_SAVE_TEXT=../crates/ferrion_lexer/tests/fuzz-regressions/<name>.java cargo fuzz run --sanitizer none --debug-assertions lex_fragments artifacts/lex_fragments/<minimized>
   ```

3. Fix the bug. `cargo test --package ferrion_lexer --test fuzz_regressions` (or `--package
   ferrion_parser`, `--package ferrion_formatter`, `--package ferrion_doc_comments`, or `--package
   ferrion_classfile --test fuzz_seeds`) runs every file there through the same checks, on the stable toolchain.

The class file targets' seeds in `fuzz/seeds/` are written by test code, never copied from a JDK:
`cargo test --package ferrion_classfile --test fuzz_seeds` checks that the committed seeds are what
`ferrion_classfile::testing::fuzz_seeds` writes, and `FERRION_WRITE_FUZZ_SEEDS=1` rewrites them.

## Pull requests

- Keep each pull request focused on one change.
- Write commit messages with a short, imperative subject line ("Add lexer support for text
  blocks"), and a body wrapped at 72 columns that explains what changed and why.
- Complete the checklist in the pull-request template, including the provenance item.

### Rebase, don't merge

History on `main` is linear, so each commit can be read, bisected, and reverted on its own.

- **Branch from `main`, and rebase to catch up.** Bring a branch up to date with `main` by
  rebasing it, not by merging `main` into it:

  ```bash
  git fetch origin
  ```

  ```bash
  git rebase origin/main
  ```

  Then push with `git push --force-with-lease`, which refuses to overwrite commits on the remote
  that you haven't seen.
- **No merge commits in a pull request.** Combine work from several branches by rebasing one onto
  another, not by merging them.
- **Each commit stands on its own.** Every commit builds and passes the checks above, and does one
  thing. Before review, tidy the series with `git rebase -i origin/main`: squash fixups into the
  commit they fix, and split commits that do several things. Address review feedback the same
  way, with `git commit --fixup` and `git rebase -i --autosquash`, rather than with "fix review"
  commits.
- **Pull requests land by rebasing** them onto `main`, never with a merge commit. A pull request
  whose commits don't stand on their own is squashed into one instead.
