# Contributing to Ferrion

Thanks for your interest in Ferrion. This document covers how contributions are licensed, the
clean-room policy every contribution must follow, and how to build and test the project.

What Ferrion is and is not is defined in [docs/SCOPE.md](docs/SCOPE.md), and the order of work is
in [docs/ROADMAP.md](docs/ROADMAP.md). A change that would alter the scope starts as a change to
SCOPE.md, discussed in an issue before any code is written.

## Licensing

[Apache License, Version 2.0](LICENSE-APACHE), at the user's option.

Unless you explicitly state otherwise, any contribution you intentionally submit for inclusion in
Ferrion, as defined in the Apache-2.0 license, is dual-licensed as above, without any additional
terms or conditions.

Source files do not carry license headers. The license files at the repository root cover
everything in it, except third-party code that keeps its own notice (see
[Code you may copy](#code-you-may-copy)).

## Clean-room policy

Ferrion replaces tools such as Google Java Format, Checkstyle, PMD, Error Prone, and SpotBugs, and it
is checked against javac. Most of those tools are licensed in ways that are not compatible with
Ferrion's licensing. Ferrion must be an independent implementation, so every contribution follows
this policy.

Automated checks (ScanCode in CI) catch copied license notices and copyright statements, but they
cannot detect copied code without them, or a port from Java to Rust. This policy, and the checklist item in the pull-request
template, are the main safeguards.

### What you may use

- **Documentation:** user guides, rule descriptions, and published style guides of upstream tools.
- **Specifications:** the Java Language Specification, the Java Virtual Machine Specification, JEPs,
  and similar documents. Cite them by section number in comments rather than quoting them at length.
- **Observable behavior:** running an upstream tool and studying what it produces. "What does javac
  report for this input?" is answered by running javac, and the answer becomes a test.
- **Names and concepts:** rule names, option names, and general ideas. Rule documentation is written
  in your own words and may link to the upstream documentation it relates to.
- **Test inputs fetched at test time:** externally licensed test suites (for example, OpenJDK's) may
  be downloaded by test tooling. They are never committed (see
  [Test inputs](#test-inputs)).

### What you may not do

- **Copy** code from a project whose license is not compatible (see
  [Code you may copy](#code-you-may-copy)). That includes code, comments, test files, and
  documentation text.
- **Port** such code: translating it from Java (or any other language) to Rust, or reproducing its
  structure, control flow, or data layout, even if every line is rewritten.
- **Work from the source:** have upstream source code open, or consult it, while writing the
  equivalent part of Ferrion. If a question can only be answered by reading upstream source, answer
  it by running the tool on test inputs instead.
- **Ask an AI assistant to do any of the above.** Code generated by an AI tool is your contribution
  and falls under this policy. Do not prompt a tool to port, translate, or reproduce upstream code,
  and review generated code with that risk in mind.

If you have studied an upstream tool's implementation of something in depth, say so in your pull
request before contributing an implementation of the same thing. That's not automatically a problem,
but it needs to be visible.

### Code you may copy

Code from another project may be copied only if its license allows it to be distributed under both
MIT and Apache-2.0. In practice, that means permissive licenses such as MIT, BSD-2-Clause,
BSD-3-Clause, ISC, and Zlib. Code licensed only under Apache-2.0 does not qualify on its own, because
it could not be offered under MIT. Copyleft licenses (GPL, LGPL, EPL, MPL) never qualify.

When you copy qualifying code:

- keep its copyright and license notice next to the copied code;
- say in the pull request where it came from and under what license;
- prefer depending on the project as a crate over copying, when that's practical.

### Test inputs

- Write your own test inputs where you can. Small, focused inputs make better tests anyway.
- Files from projects with incompatible licenses (for example, OpenJDK's GPL test suites, or test
  files from Checkstyle, PMD, or SpotBugs) are fetched by the test tooling at test time and are
  never committed.
- Corpus projects are fetched by `tools/corpus`, pinned to a commit. Nothing it fetches is
  committed.
- Expected output generated by running an upstream tool on Ferrion's own test inputs may be
  committed.

### Dependencies

Third-party crates are welcome if they pass `cargo deny check`, which enforces the allowed license
list in CI. The same rule applies to dependencies of the Maven plugin and the IntelliJ extension.
The lexer and parser are hand-written; parser generators are not used.

### Reporting a concern

If you believe something in Ferrion was copied or ported in violation of this policy, open an issue.
Concerns are taken seriously, and code with unclear provenance is removed or rewritten.

## Development

### Prerequisites

- **Rust:** install [rustup](https://rustup.rs). The toolchain version is pinned in
  `rust-toolchain.toml`, and rustup installs it automatically.
- **A JDK:** needed only for the javac oracle and corpus tools. Use the newest GA release to cover
  the latest language features.
- **Maven:** needed only for the javac oracle and the Maven plugin.
- **Python 3.13 and libmagic:** needed only to run ScanCode locally. On macOS, install libmagic with
  `brew install libmagic`.

### Checks

CI runs the following, and each must pass before a change is merged:

```bash
cargo fmt --all --check
```

```bash
cargo clippy --workspace --all-targets -- -D warnings
```

```bash
cargo test --workspace
```

```bash
cargo deny check
```

```bash
python3 tools/scancode/scan.py
```

The ScanCode check installs its pinned dependencies from `tools/scancode/requirements.txt` into
`target/scancode/venv`, then fails on any license other than MIT or Apache-2.0, or any copyright
holder other than Ferrion's.

### Corpus

The corpus projects are listed in `tools/corpus/projects.toml`, each pinned to a commit. They are
fetched into `target/corpus`, or into `FERRION_CORPUS_DIR` if it is set:

```bash
cargo corpus fetch
```

Each project's lock file in `tools/corpus/lock/` records its source sets, Java releases, and
dependency jars, so fetching never runs a project's build. After adding a project or changing its
commit, regenerate its lock file with `JAVA_HOME` set to the JDK named in `projects.toml`. This runs
the project's own build:

```bash
cargo corpus lock <project>
```

### javac oracle

`tools/javac-oracle` dumps javac's tokens, comments, parse diagnostics, and tree positions as JSON
lines. Build it with the newest GA JDK:

```bash
mvn --batch-mode --file tools/javac-oracle/pom.xml package
```

```bash
java -jar tools/javac-oracle/target/javac-oracle.jar --release 17 Example.java
```

### Tests

- Every bug fix comes with a regression test.
- Fuzz failures are reduced and kept as regression tests.
- Generated rule documentation is checked in CI, so regenerate it when rule metadata changes.

### Fuzzing

The fuzz targets are in `fuzz/`, a [cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz) project
with its own workspace. It builds with the nightly toolchain pinned in `fuzz/rust-toolchain.toml`,
which rustup uses for commands run from `fuzz/`; everything else stays on the stable toolchain. Run
the commands below from `fuzz/`, after installing the toolchain and cargo-fuzz once:

```bash
rustup toolchain install && cargo install cargo-fuzz --version 0.13.2 --locked
```

- `lex` reads arbitrary bytes as a source file and lexes its text.
- `lex_fragments` lexes text built from fragments of Java, such as keywords, comment and text block
  delimiters, and Unicode escapes, to reach states that random bytes rarely do.

Both fail when `ferrion_lexer::invariants` finds that the lexer broke a promise its API documents,
or when the lexer panics. Run a target, reading the committed seeds in `seeds/` and keeping what it
finds in `corpus/` (ignored by git):

```bash
mkdir -p corpus/lex && cargo fuzz run --sanitizer none --debug-assertions lex corpus/lex seeds/lex -- -dict=java.dict -timeout=10
```

The lexer has no unsafe code, so AddressSanitizer is turned off, which makes fuzzing about twice as
fast; debug assertions catch arithmetic overflow. Pass the same two flags to every `cargo fuzz`
command, or it rebuilds the targets. Add `-max_total_time=<seconds>` after `--` to stop after a
while. CI runs every target for 60 seconds (`.github/workflows/fuzz.yml`, called from `ci.yml`), and
a weekly scheduled run of the same workflow runs each for 30 minutes and keeps its corpus in the
Actions cache. Crashing inputs are uploaded as the `fuzz-artifacts` artifact.

To turn a failure into a regression test:

1. Minimize the input. `tmin` prints the path of the minimized input:

   ```bash
   cargo fuzz tmin --sanitizer none --debug-assertions lex artifacts/lex/crash-<hash>
   ```

2. Copy it to `crates/ferrion_lexer/tests/fuzz-regressions/`, under a name that says what it
   covers. A `lex_fragments` input is a list of fragment numbers, not source text, so write its text
   there instead:

   ```bash
   FERRION_FUZZ_SAVE_TEXT=../crates/ferrion_lexer/tests/fuzz-regressions/<name>.java cargo fuzz run --sanitizer none --debug-assertions lex_fragments artifacts/lex_fragments/<minimized>
   ```

3. Fix the bug. `cargo test --package ferrion_lexer --test fuzz_regressions` runs every file there
   through the same checks, on the stable toolchain.

## Pull requests

- Keep each pull request focused on one change.
- Write commit messages with a short, imperative subject line ("Add lexer support for text
  blocks"), and a body wrapped at 72 columns that explains what changed and why.
- Complete the checklist in the pull-request template, including the provenance item.
